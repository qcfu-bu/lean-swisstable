# SwissTable: architecture of a verified drop-in for `Std.HashMap` and `Std.HashSet`

Status: implemented, 2026-10-24. Target: Lean v4.35.0, core and Std only (no Mathlib). The design
below is what was built; the bake-off chose the SwissTable layout (`docs/bakeoff/decision.md`),
whose core `SwissTable.Core.Swiss` is selected (section 3.7), and the measured performance is in
section 9.4. Where the text says a step is still to come, section 3.7 and 9.4 give the outcome.
Inputs: `inventory.md`/`inventory.json` (the API to reproduce), `proofs.md` (the proof
architecture and its mock experiments), `parity.md` (the statement checker). All three are in
this directory. Small module-system experiments made for this document are in `modtest/` (their
outputs are recorded in `modtest/results.log`), and a section-dependency script is in
`tools2/secdeps.py`.

## 0. Decisions in brief

1. **One standalone lake package `swisstable`**, namespace `SwissTable`, types
   `SwissTable.HashMap α β` and `SwissTable.HashSet α`. File and module names mirror Std
   (`SwissTable.HashMap.Basic`, `SwissTable.HashMap.Lemmas`, …) so that `import Std.Data.HashMap`
   becomes `import SwissTable.HashMap`.
2. **Layering.** A layout-specific core (`SwissTable.Core.Table`, chosen by the bake-off) exports
   23 definitions and 22 model lemmas over `toListModel : Table α β → List ((_ : α) × β)`.
   Everything above it is layout-free: derived queries and traversals, Std's bulk algorithms
   (insertMany, ofList, union, inter, diff, beq), the user API, the model bridge, and the
   1,011 user lemmas.
3. **Proof strategy: Std's own architecture collapsed to one layer** (approach (a) of
   `proofs.md`). The 678 HashMap lemmas are proved by a copy of Std's `simp_to_model` macro with
   Std's own `using` terms, generated by `tools/port.py`. The 320 HashSet lemmas are copied
   verbatim, because HashSet is Std's wrapper around `HashMap α Unit`. The transfer to
   `Std.ExtHashMap` (approach (b)) is rejected; section 5 says why.
4. **The core is sealed by the module system.** Core definitions are `public` but not
   `@[expose]`d. Importing modules cannot unfold them, while `@[inline]` and `@[specialize]`
   still work across modules (checked in `modtest/`, section 2.3). The swap-safety rule ("layers
   above the core use only the 45 contract names") is checked mechanically.
5. **A list-backed reference core** (`SwissTable.Core.ListRef`) satisfies the same contract. Every
   layer above the core is developed and proved against it, in parallel with the real core, and
   the real core is switched in by changing one import line.
6. **Parity is a test.** `Parity.run` runs inside the test library `SwissTableTest`, so `lake test`
   fails when a statement, binder, attribute or instance differs from Std, or when a theorem
   depends on `sorry`.

## 1. Fixed requirements

These come from the task and from the study (`inventory.md`, "Drop-in notes"):

* **Same declarations.** All 1,011 public theorems (688 HashMap, 323 HashSet), 81
  definitions and 35 instances, with the same names, elaborated statements, binder kinds,
  binder names, default values and attributes (simp, grind kinds, `cbv_eval`, `cbv_opaque`,
  `refl`, `symm`, `elab_as_elim`, one `deprecated` alias, 10 `grind_pattern` commands, the late
  `attribute [simp] contains_eq_false_iff_not_mem`).
* **No extra typeclass requirements.** In particular no `Inhabited α` or `Inhabited β` on
  `emptyWithCapacity`, `insert`, `filter` and the rest.
* **Std's semantics.** `insert` replaces the stored key and the value, `insertIfNew` and
  `HashSet.insert` keep the old entry, `modify` and `alter` (when `f` returns `some`) replace
  the stored key by the argument key, `insertMany` and `ofList` are left folds of
  `insert` (last occurrence wins), `HashSet.insertMany` and `HashSet.ofList` keep the first
  occurrence, `union` is right-biased, `inter` keeps the entries of `m₁`.
* **The 45 structural equalities** (`ofList_nil`, `insertMany_cons`, `erase_emptyWithCapacity`,
  `containsThenInsert_snd`, …) hold as equalities of maps, not up to `~m`.
* **One iteration order.** `toList`, `keys`, `values`, `toArray`, `keysArray`, `fold`,
  `foldM`, `forM`, `forIn`, `all`, `any` and the iterators all enumerate the same sequence.
* **Faster than Std**, measured by `bench/` (section 9.4).
* **Deferred:** DHashMap, `Raw`, `ExtHashMap`, `ExtHashSet`.

Accepted differences that cannot be avoided, listed in the parity configuration (section 9.1):
the `inner` field and constructor of `HashMap` (Std's has type `DHashMap α (fun _ => β)`), the
`Equiv.inner` field, the elaborated state type of the four iterator definitions and their 12
lemmas, and the `Repr` output prefix (section 11, question Q5).

The Lemmas files keep Std's order and each imports the previous one, so the cut points do not
change which sibling lemmas are in scope. `tools2/secdeps.py` finds that Std's proofs cross these

every file's statements exist from the start (section 10).

### 2.3 Module-system conventions

Every file of the library starts with `module`, as Std's do. The rules, with what
`modtest/` showed on v4.35.0:

* **Core files**: `public section` without `@[expose]`. Importing modules cannot `unfold`,
  `simp [def]` or `rfl` through core definitions (`ModC.lean`: "Tactic `unfold` failed").
  Cross-module `@[inline]` and `@[specialize]` still work (`ModB.lean` with
  `trace.compiler.ir.result`: the inlined body and a `T.app._at_.useF.spec_0` specialisation
  appear in the importer's IR). The only exposed core definition is `Table.markLinear`, because
  `HashMap.markLinear_eq` must be `rfl` (it carries `@[defeq]` in Std).
* **Inside a module, an exported theorem cannot be proved by `rfl` through a non-exposed
  definition of the same module** (`ModRfl.lean`: "This theorem is exported from the current
  module. This requires that all definitions that need to be unfolded … must be exposed").
  `unfold d`, `simp [d]` and ordinary term proofs that need the unfolding do work in the same
  module (`ModM.lean`); only `rfl` proofs, which would become `@[defeq]`, are restricted. So core
  and `Derived` lemmas about their own definitions are proved with `unfold`/`simp only [d]`,
  never `rfl`. This also keeps them from becoming dsimp lemmas, which `proofs.md` §9.8 showed to
  break `getKey!_alter`.
* **`Derived.lean` and `Bulk.lean`** are not exposed either. **`HashMap/Basic.lean`,
  `AdditionalOperations.lean` and `HashSet/Basic.lean` are `@[expose] public section`**, as
  Std's are. Std's 12 `@[defeq]` theorems (`get?_eq_getElem?`, `get_eq_getElem`,
  `get!_eq_getElem!`, `insert_eq_insert`, `singleton_eq_insert`, `markLinear_eq`,
  `forIn_eq_forIn`, `forM_eq_forM` and four HashSet ones, listed by `modtest/DefeqList.lean`)
  only unfold these wrapper files and instances, so they stay `rfl`.
* **Layer 2 files never `import all`** a core or `Derived` module (Std's Lemmas.lean does
  `import all Std.Data.DHashMap.Basic`; ours must not). `tools/ci.sh` greps for it.
* **`Tactic.lean`** needs `public meta import Std.Data.HashMap.Basic`, because its lemma tables
  are `Std.HashMap`s used at macro-expansion time. `modtest/ModTac2.lean` builds the full
  `simp_to_model` shape (lemma table, location, `using`, discharger) in a module and
  `ModTac2Use.lean` uses it from another module. Keep `Mock2.lean`'s quotation layout, with
  `$[apply …];*` on its own line: a one-line variant does not parse.
* **`Model.toListModel` lives at the top of `HashMap/Basic.lean`** (exposed, namespace
  `SwissTable.Model`), and `Equiv`'s field is stated with it. Std's `using` terms pass `h.1` to list
  lemmas in files far from `Basic`; with the field typed by the model itself, `h.1` has exactly
  the type the rewritten goal mentions and no cross-module unfolding is needed. `Table.toListModel`
  below it stays sealed.
* Non-module importers (`ModD.lean`) can unfold everything. This matters only for the test files,
  which are plain files, and it is harmless there.
* Declare `universe u v w w'` in Std's order. Parity matches universes by first occurrence and
  warns on every declaration when the order differs.

## 3. The core contract (the interface the bake-off winner implements)

### 3.1 Shape

```lean
namespace SwissTable.Core
/-- The table, with its invariant bundled. Layout-specific; opaque to everything above. -/
structure Table (α : Type u) (β : Type v) [BEq α] [Hashable α] : Type (max u v) where
  ...                      -- arrays, size, capacity data, and `wf : WF ...`
```

`HashMap` wraps it, exactly as Std's wraps `DHashMap`:

```lean
structure HashMap (α : Type u) (β : Type v) [BEq α] [Hashable α] where
  /-- Internal implementation detail of the hash map -/
  inner : SwissTable.Core.Table α β
```

A one-field structure is represented by its field at runtime, so the wrapper costs nothing.

The invariant is bundled, and the part that needs lawful instances is guarded inside it, as in
the existing map (`WF.probe [EquivBEq α] [LawfulHashable α] : ProbeInv`). Distinct keys
therefore come for free under lawfulness, and no lemma takes a well-formedness hypothesis.

The only observable model is `toListModel`, a sigma list. That is the type every
`Std.Internal.List` operation and lemma uses (`getValue?`, `insertEntry`, `eraseKey`,
`Const.alterKey`, `insertListConst`, …), so Std's `using` terms apply unchanged
(`proofs.md` §3).

### 3.2 Primitive definitions (23)

The core has to define exactly these, with these signatures, in namespace `SwissTable.Core.Table`.
Everything else is derived in `Derived.lean`/`Bulk.lean`.

| # | name | signature (after `[BEq α] [Hashable α]`) | note |
|---|---|---|---|
| 1 | `Table` | `(α : Type u) → (β : Type v) → [BEq α] → [Hashable α] → Type (max u v)` | |
| 2 | `toListModel` | `Table α β → List ((_ : α) × β)` | proof-only; may be computable |

| 8 | `contains` | `Table α β → α → Bool` | |
| 9 | `lookupMem` | `{σ : Type w} → (t : Table α β) → (a : α) → t.contains a = true → (α → β → σ) → σ` | `@[inline]`; for `get`, `getKey` |

| 23 | `forIn` | `{ε : Type w} {m : Type w → Type w'} [Monad m] → (α → β → ε → m (ForInStep ε)) → ε → Table α β → m ε` | early exit, for `all`/`any`/`for` |

Why this set:

* **Queries go through one continuation-passing probe.** `lookup t a found missing` is
  `@[inline]`, so at each call site the continuations are known lambdas and are beta-reduced. The
  probe loop inside stays a single `@[specialize]`d function. Eight queries are then one-line
  derived definitions with derived lemmas: `get?`, `getD`, `get!`, `getKey?`, `getKeyD` and
  `getKey!` through `lookup`, and `get` and `getKey` through `lookupMem` (`inter` also calls
  `lookup` directly). A core proves two lookup lemmas instead of twelve query lemmas. `contains`
  is kept primitive only so that `lookupMem` can mention it in its type.
* **The fused operations, `alter` and `modify` are primitives** because a faithful derived
  definition probes twice (`(t.contains a, t.insert a b)`), and Std probes once.
* **One monadic fold, one reverse fold, one early-exit loop** cover all eleven traversals
  (section 4.1).

### 3.3 Primitive lemmas (22)

**U** means the lemma holds with no hypotheses on `BEq`/`Hashable`. **L** means it takes
`[EquivBEq α] [LawfulHashable α]`. The split is forced by Std: a user lemma stated without
lawfulness can only be proved from U lemmas (`proofs.md` §4). All lemmas take the instances as
`{_ : BEq α} {_ : Hashable α}`, as Std's do, so they apply to whatever instances a map was built
with.

The list functions are `Std.Internal.List.*`, the same names Std's `WF.lean` uses (lemmas 12–19

lemmas 4, 6, 7 and 8 replace the twelve query lemmas and the four empty-map queries, 20–22

is derived once, in `Derived.lean`. `alter` and `modify` stay core obligations (they could be
derived with two probes, see Q3).

### 3.5 What any layout must satisfy

These follow from Std's statements and from the contract. They are input to the bake-off; the
first six repeat `proofs.md` §9 in contract terms.

1. **U lemmas without lawfulness.** `size_eq_length`, `toListModel_filter`, `filterMap`,
   `map` and the three traversal lemmas must hold for any `BEq`/`Hashable`. For an
   open-addressing table this means `filter` must preserve the entry multiset without relying
   on the probe invariant. Rebuilding by reinsertion that never compares keys (by stored tag, as
   the existing `grow` does: `toList_grow_perm` needs no `EquivBEq`) is the easy route. Deleting
   in place by backward shift needs a proof that the shift only moves entries, made without the
   probe invariant.
2. **Erase on a miss returns its argument.** Otherwise `erase_emptyWithCapacity` is not an
   equality. This is also the fast path.
3. **Fused operations share the probe.** `containsThenInsert_eq` and its two siblings are U
   equalities of tables, so define `insert t a b := (t.containsThenInsert a b).2` (or the reverse,
   both from one probe-and-write function). Then they hold by `unfold`.
4. **`insert`, `modify` and `alter` replace the stored key.** `Const.modifyKey` writes
   `replaceEntry a (f v)` and `Const.alterKey` writes `insertEntry a v`, both with the argument
   key `a`, so on a hit all three write `a` into the slot, not only the new value (Std's runtime
   does the same). A `modify` that keeps the stored key cannot prove `toListModel_modify`. In the
   linear-probing layout this is free: the probe stops at a hit only when the slot's tag equals
   the new key's tag, so writing the new key keeps the unconditional tag invariant (`TagInv`),
   and the probe invariant is unaffected under lawfulness.
5. **No `Inhabited`.** Layouts with one key cell and one value cell per slot (linear, Swiss) have
   no placeholder for empty slots. The scheme: `emptyWithCapacity c` allocates nothing (all
   arrays empty, the capacity hint stored in a field), and the first insert allocates the slot
   arrays with the inserted key and value as filler. Growth uses the key being inserted as filler,
   `map` and `filterMap` use the first mapped value, and a rebuild that keeps no entry returns the
   unallocated table. The invariant gets a second shape ("unallocated: every array empty,
   `size = 0`"), and a probe needs one capacity-zero check. The dense layout (entries array plus
   index table) stores only live entries and needs no filler. `implemented_by`, `unsafeCast` and
   the like are excluded (spec-integrity rule: no new axioms, `sorry` or `implemented_by`).
6. **`toListModel` order is the iteration order.** For slot layouts it is slot order. For the
   dense layout it is the entries array.
7. **`markLinear` is exposed and definitionally the identity** (`⟨t.keys.markLinear, …⟩` with
   `Array.markLinear xs := xs`, as Std's `Raw.markLinear`).
8. **Speed.** `lookup`, `contains`, `insert` and the fused operations must specialise to scalar
   code at `Nat` keys (inspect with `set_option trace.compiler.ir.result true`). `Derived`'s
   one-line queries are only free if `lookup` inlines.

The earlier map in `Wnetkat2/Data/OAMap` (since replaced by this library and deleted) (layout "three arrays, 62-bit tags, linear probing")
already covers parts of lemmas 1, 2, 3, 7, 12, 13 and 20–22. Its `Slots.entries : List (α × β)`
becomes `toListModel` by `map (fun p => ⟨p.1, p.2⟩)`, and `entries_pairwise`, `lookup_entries`,
`entries_setNew_perm` and `entries_grow_perm` carry over. Missing: erase by backward shift
(the largest piece), alter/modify, filter/filterMap/map, the monadic traversals, the fused
operations other than `getThenInsertIfNew?`, key replacement, and the `Inhabited`-free shape.

### 3.6 The reference core `SwissTable.Core.ListRef`

### 3.7 The selected core `SwissTable.Core.Swiss`

The bake-off (`docs/bakeoff/`) chose hashbrown's generic layout: a byte array of control bytes
(EMPTY `0xFF`, DELETED `0x80`, FULL `0b0hhhhhhh` with a 7-bit tag), `cap + 8` long with the first
group mirrored at the end, and two arrays of `cap + 1` key and value cells; load 7/8; groups of 8
control bytes read as one little-endian word with exact per-lane tag matching; triangular probing
over groups; one insertion probe with a fast path at an EMPTY home slot; tombstones by the 8-window
rule; every rebuild into a fresh table, moving each entry to the first free slot of its probe
(rehashing its key, comparing none). Its 23 definitions stay sealed and are one-liners: most wrap
an exposed `Swiss.*Impl` definition, and the fused ones are defined from each other as §3.5 item 3
asks; each has an equation lemma `Table.*_def` for the proof files. The invariant `Swiss.WF` is the
erased field `Table.wf`, with the probe and distinctness parts under
`[EquivBEq α] [LawfulHashable α]` (§3.1). Section 3.5 is met as follows:

1. `filter`, `filterMap` and `map` erase or rewrite in place and compare no keys, and neither does
   the rebuild. The U lemmas hold with no lawfulness.
2. `erase` returns its argument when the probe misses; the unallocated table (`cap = 0`) always
   misses.
3. `insert := (containsThenInsert ..).2` and `insertIfNew`, `containsThenInsertIfNew` from
   `getThenInsertIfNew?`, each one probe and one write.
4. A hit writes the argument key (the tag matched, so `TagInv` holds unconditionally).
5. No `Inhabited`: the empty map allocates no array (a shared group of 8 EMPTY bytes, `#[]`
   arrays); the first insert, and every rebuild, takes the inserted pair as the placeholder of the
   free cells; `filterMap` and `map` take the first mapped value. At most one erased pair stays
   referenced, until the next rebuild.
6. `toListModel` is the full slots in slot order, and every traversal goes in slot order a group
   at a time (`foldRev` in reverse).
7. `markLinear` marks the three arrays.
8. Lookups, inserts and erases specialise to scalar code (`tools/check_c.py`, §9.3).

Every operation runs on `USize` indices on tables of at most `2 ^ 31` slots and on `Nat` indices
beyond (the same algorithms; one guard at the top of each operation). The proofs (6,610 lines in
`SwissTable/Core/Swiss/Proofs/`, plus the 1,349-line SWAR library `Group.lean`) only add erased
arguments, so the code is the frozen version measured in the bake-off: instructions per operation of
`SwissTable.HashMap` on the bake-off harness equal the frozen core's (ratio 1.0002 over 36 cells).
The layers above the core needed no change when it was selected.

## 5. Proof-derivation strategy, and why

**Chosen: (a), Std's design with its middle layers removed.** Std proves HashMap lemmas in
four layers. HashMap delegates to DHashMap (548 of 678 proofs are one term), DHashMap delegates
to `Raw₀` (unbundling the invariant), and `RawLemmas.lean` proves 631 of its 828 theorems by
`simp_to_model … using List.foo`. Only `WF.lean` and `Internal/List/Associative.lean` contain
real work. Our map bundles its invariant and has no Raw variant, so Layers 0–1 (core, model
lemmas) sit directly under the user lemmas, and each user lemma's proof is the bottom of Std's
chain: `simp_to_model [queries] using <Std's List lemma>`.

Evidence (`proofs.md` §10): on a random sample of 50 lemmas, 47 port with no hand edit and
compile against the sealed mock, 2 need 2-line hand proofs, and 1 is a Layer 1 obligation.
`tools/port.py` run on all 678 HashMap lemmas yields 502 certain one-liners or copies, 128
adapted RawLemmas texts to be checked by compiling, and 48 flagged (29 of them Layer 1/1.5
equalities). HashSet's 320 lemmas port verbatim (all 16 sampled compiled).

**Rejected: (b), transfer to `Std.ExtHashMap`** (`Mock3.lean`). It works where it applies,
including the dependent `getElem_insert`, but:

* only 402 of the 678 statements exist identically in ExtHashMap, and the 214 missing names are
  all iteration, `Equiv`, `isEmpty` and `emptyWithCapacity` lemmas;
* every ExtHashMap operation needs `[EquivBEq α] [LawfulHashable α]`, so none of the 126 HashMap
  lemmas stated without lawfulness can transfer;
* its transfer lemmas (`absE (m.insert k v) = (absE m).insert k v`) are proved from our own
  query lemmas, so it needs approach (a) underneath (109 lines in the mock for 7 queries and 2
  operations);
* under (a) each proof is already a generated one-liner, so (b) saves nothing per lemma.

Transferring to `Std.HashMap` up to `~m` would bring back iteration and `Equiv`, but `simp`
cannot push the abstraction through nested operations without setoid rewriting, and the
order-sensitive lemmas (`fold_eq_foldl_toList`) still need the model. `Mock3.lean`'s `port`
tactic can stay available as a fallback in the porting script; the sample did not need it.

    <;> try wf_finish)

### 6.2 The porting pipeline

`tools/port.py` (from this directory, extended in Wave 1) reads Std's sources and writes the
nine `HashMap/Lemmas/*.lean` files. For each theorem it keeps Std's attributes and statement
text unchanged and builds the proof as in `proofs.md` §6:

1. a HashMap proof that does not mention `DHashMap` is copied (siblings, `rfl`, `by simp`);
2. otherwise a DHashMap proof that does not mention `Raw₀` is copied with DHashMap names renamed
   to HashMap names (the rename map comes from Std's 548 delegation lines);
3. otherwise a RawLemmas proof of the form `[revert h;] simp_to_model [qs] using T` becomes
   `simp_to_model [qs'] [at *] using T'` (queries renamed, `contains` → `contains, mem`,
   `at *` when the statement has hypotheses and `T` does not use `h.1`, Raw₀ siblings renamed
   and their `_ h` arguments dropped);
4. otherwise the renamed RawLemmas text is emitted with a `-- REVIEW` mark;
5. a proof `ext DHashMap.X` or `ext DHashMap.Const.X` (the 25 Layer 1/1.5 equalities, for
   which the script currently finds no RawLemmas proof and emits `sorry`) becomes
   `ext Core.Table.X` (section 6.3); anything still unmatched is emitted as `sorry` with
   `-- REVIEW`.

Wave-1 extensions, all found by the sample: the 13 `Equiv` constructions written `⟨…⟩` in Std
(emit `⟨by simp_to_model [Equiv, op] using List.…_of_perm …⟩`); the 6 statements containing
`haveI … :=` (the `getElem_alter` family), where the statement/proof split is currently wrong;
`insertMany_ind` uses, which take the bundled motive
(`insertMany_ind (motive := fun m => k ∈ m) m h fun _ _ _ h => mem_insert.2 (Or.inr h)`);
and the non-theorem commands (section 6.4).

Since the Merge the generated files are reproduced exactly. A proof that no candidate supplies
is written by hand in `tools/data/hand.json` (Std name ↦ the text after the statement; 56
entries), never in the generated file, and each file's module docstring lists its hand proofs.
`python3 -I tools/port.py lemmas --check` regenerates in memory and fails on any difference, and
`tools/ci.sh` runs it. Statements always come from Std's text. The splitter (`tools/split.py`) cuts at the Std line
numbers in section 2.2 and gives every file the preamble that is active at its cut point: module
header, imports, `variable {α : Type u} {β : Type v} {γ : Type w} {δ : Type w'} {_ : BEq α}
{_ : Hashable α}`, `namespace SwissTable.HashMap`, the open `section`s with their `variable` lines
(the first file pair cuts inside Std's first anonymous section, so `GetKey.lean` re-declares
`variable {m : HashMap α β}`), and `open Std.Internal.List` for proofs. Std's three-line
`private theorem ext {m m' : HashMap α β} : m.inner = m'.inner → m = m'` is copied, still
private, into each file that uses it, so no new public name appears.

one-line, revert-form or multi-line; V = derived proof with renamed sibling references; E =

## 7. HashSet

Exactly Std's design: `structure HashSet (α : Type u) [BEq α] [Hashable α] where inner :
HashMap α Unit`, with every operation Std's one-line wrapper (`insert m a := ⟨m.inner.insertIfNew a ()⟩`,
`get? := getKey?`, `toList := m.inner.keys`, `insertMany := insertManyIfNewUnit`,
`ofList := unitOfList`, `Equiv` with field `m₁.1.Equiv m₂.1`). Unlike HashMap, the `inner`
field and `Equiv.inner` are reproduced exactly, because their types are `SwissTable.HashMap α Unit`
and `SwissTable.HashMap.Equiv`.

* `HashSet/Basic.lean` is Std's file with `namespace Std` → `namespace SwissTable` and the imports
  changed. Inside `namespace SwissTable.HashSet`, Std's references `HashMap.foo` resolve to
  `SwissTable.HashMap.foo`, as long as no file does `open Std`.
* `HashSet/Lemmas.lean` is Std's file with the same rename and two edits:
  `DHashMap.mem_of_mem_insertIfNew'` → `Model.mem_of_mem_insertIfNew'`, and the public
  `Std.Internal.ForIn.toList_eq_of_forIn_eq` kept. 305 of its 320 proofs are a single HashMap
  lemma name and 13 are short `by` blocks over HashMap lemmas. No tactic or model is needed.
* The private `ext` is copied as is (it is file-local in Std too).
* Std defines `LawfulSingleton` for HashMap but not for HashSet; copy that asymmetry.
* Docstring conflict: Std's `HashSet.ofList` docstring says the last duplicate is kept, but the
  lemmas (`ofList_eq_insertMany_empty` with `insert = insertIfNew`) make the first one win. We
  follow the lemmas and correct the docstring.

Cost: every set carries an `Array Unit` of values (8 bytes per slot, a store per insert, a copy
on growth). Measure it in Wave 3 before building a value-less set core (Q1).

  `HashSet.iter m := (m.inner.iter.map fun e => e.1 : Iter α)`, as Std. The 12 lemmas are short:
  `toList_iter` from `Array.toList_iter` and `Model.toArray_eq…`, the `toListRev` and `toArray`
  forms from `Iter.toListRev_eq` and `Iter.toArray_toList`. The iterator is `Finite` and
  `Productive` through `ArrayIterator`'s instances, and `for x in m.iter` works through its
  `IteratorLoop`. The price is an O(n) array at creation, where Std's iterator is lazy.
* **Wave 4, lazy:** a slot-cursor state `structure SlotIter (α β) [BEq α] [Hashable α] where
  t : Core.Table α β; pos : Nat` with `Iterator`, `Finite` (measure `numSlots - pos`),
  `Productive` and `IteratorLoop` instances. It needs two more core primitives (`nextOcc :
  Table α β → Nat → Option (Nat × α × β)` and a lemma that scanning from 0 enumerates
  `toListModel`). Only do it if benchmarks show iterator use.

Parity cannot compare these 16 declarations (the elaborated state types necessarily differ), so
they are in its `ignore` list. `tools/srccheck.py` instead checks that their source text equals
Std's `src_statement` from `inventory.json` after the namespace rename.

## 9. Parity and the other checks

### 9.1 Running the parity checker

`test/Parity.lean` is this directory's checker (since the Merge it also renames the `Name` literals
of notation descriptions and has `failOnWarning`). Its defaults map
`Std.HashMap ↦ SwissTable.HashMap` and `Std.HashSet ↦ SwissTable.HashSet` and skip `Raw` and
`Internal`; the driver narrows `exclude` to the deferred `Raw` and turns on
`checkStructureInternals`, so `Internal.numBuckets`, HashSet's `inner`/`Equiv.inner` and the other
structure internals are checked too. The driver is a module of the test library, so a parity error
fails `lake test`:

```lean
-- test/SwissTableTest/ParityRun.lean   (plain file, not `module`)
import Std
import SwissTable
import Parity

/-! Statement parity of SwissTable against Std.HashMap/Std.HashSet (v4.35.0). -/
#eval Parity.run {
  ignore := #[
    -- elaborated iterator state types expose Std's AssocList; text-checked by tools/srccheck.py
    `Std.HashMap.iter, `Std.HashMap.keysIter, `Std.HashMap.valuesIter, `Std.HashSet.iter,
    `Std.HashMap.toList_iter, `Std.HashMap.toListRev_iter, `Std.HashMap.toArray_iter,
    `Std.HashMap.toList_keysIter, `Std.HashMap.toListRev_keysIter, `Std.HashMap.toArray_keysIter,
    `Std.HashMap.toList_valuesIter_eq_toList_map_snd, `Std.HashMap.toListRev_valuesIter,
    `Std.HashMap.toArray_valuesIter,
    `Std.HashSet.toList_iter, `Std.HashSet.toListRev_iter, `Std.HashSet.toArray_iter,
    -- HashMap's `inner` field is a core table, not a `DHashMap` (ARCHITECTURE §1)
    `Std.HashMap.inner, `Std.HashMap.mk, `Std.HashMap.rec, `Std.HashMap.recOn,
    `Std.HashMap.casesOn, `Std.HashMap.mk.noConfusion, `Std.HashMap.mk.inj,
    `Std.HashMap.mk.injEq, `Std.HashMap.mk.sizeOf_spec,
    `Std.HashMap.Equiv.inner, `Std.HashMap.Equiv.mk, `Std.HashMap.Equiv.rec,
    `Std.HashMap.Equiv.recOn, `Std.HashMap.Equiv.casesOn],
  exclude := #[`Std.HashMap.Raw, `Std.HashSet.Raw],
  checkStructureInternals := true,
  jsonOut := some ".lake/parity.json",
  failOnWarning := true }
```

(Keep every field of the `{ … }` at the indentation of the first field, or Lean fails with
"expected '}'", `parity.md`.) Run it alone with
`lake build SwissTable Parity && lake env lean test/SwissTableTest/ParityRun.lean`, or with
`maxShow := 20, showMissingStatements := true, failOnError := false` as a to-do list during
Waves 1–2 (it prints the translated Std statement of each missing declaration, and
`checkAxioms` lists every theorem that still depends on `sorry`). A full run takes about 2 s.

What it enforces, from `parity.md`: elaborated statements equal up to binder names and proofs
inside statements, exact binder kinds and default values (`capacity := 8`), aligned binder
telescopes (extra, missing and moved hypotheses), binder names (warning), instance types (with
renaming by type), all simp and grind facts, `cbv_eval`, `cbv_opaque`, `defeq`, `refl`, `symm`,
`ext`, `elab_as_elim`, `deprecated`, instance priority, reducibility and `protected`; extras;
and `sorryAx` (error) or non-standard axioms (warning). The axiom check stays valid for a
library built with the module system: `Lean.collectAxioms` reports `sorryAx` for an imported
module theorem even though its body is not part of the public view (`modtest/ModSUse.lean`).
Structure internals (`mk`, `inner`, `rec`, `Equiv.mk`, `Equiv.inner`) are not checked by
default. The driver checks them and ignores exactly the 14 that necessarily differ because
HashMap's `inner` is a core table: `HashMap.{inner, mk, rec, recOn, casesOn, mk.noConfusion,
mk.inj, mk.injEq, mk.sizeOf_spec}` and `HashMap.Equiv.{inner, mk, rec, recOn, casesOn}`. With
the 16 iterator declarations that makes 30 ignored names; 1140 declarations are checked.

Two known items to watch on the first real run. Std's `get.congr_simp`/`getKey.congr_simp` are
reserved names realised on demand; if ours are reported missing, add
`#check @SwissTable.HashMap.get.congr_simp` (and the other two) before `#eval` so they are realised.
The auto-generated instance names must match; they do when Std's text is copied (section 4.3),
and the checker falls back to matching by type otherwise.

## 11. Risks and open questions

### Risks

* **The U lemmas constrain the layout.** `toListModel_filter`, `toListModel_filterMap`,
  `toListModel_map`, `size_eq_length` and the traversal lemmas must hold without lawfulness, and
  `erase_emptyWithCapacity` plus the three fused-operation lemmas are equalities of tables. A
  layout whose `filter` deletes in place under the probe invariant cannot prove the first one
  without extra work. Each bake-off candidate should show a plan for section 3.5 before it wins.
* **`Inhabited`-free tables add an invariant shape** (unallocated versus allocated) to the slot
  layouts and a branch to the probe. The dense layout avoids this. Measure the branch.
* **`Std.Internal.List` is internal** and carries no stability promise. It appears only in core,
  `Derived`, `Bulk`, `Model` and proofs, never in user statements. Pin v4.35.0; on upgrade, rerun
  `tools/port.py` on the new sources (statements and `using` terms both come from there; the
  hand proofs of `tools/data/hand.json` are re-emitted and may need fixing), rerun `inventory`
  and parity.
* **Estimated, not measured:** 128 of the generated proofs are adapted RawLemmas text checked
  only by compiling (3 of 4 compiled in the sample). Budget about 50 hand fixes.
* **simp normal forms.** Some `using` terms depend on `Bool.not_eq_true` and `ite` condition
  shapes. A Model lemma that became a dsimp lemma would change these (the `getKey!_alter`
  failure in `proofs.md` §9.8). The module system prevents `rfl` proofs of core and `Derived`
  lemmas (section 2.3); Model lemmas are theorem applications, which is fine.
* **Parity does not compare definition bodies.** Semantics are pinned only as far as Std's
  lemmas pin them. Unverified functions (`partition`, `values` order, `valuesArray`, `Repr`,
  `Internal.numBuckets`) are covered by `#guard` tests only.
* **Name clashes for users.** Code that does `open Std` and writes `HashMap` becomes ambiguous if it
  also opens `SwissTable`. Document the switch as "replace `Std.HashMap` by `SwissTable.HashMap`" or
  `open Std hiding HashMap HashSet` followed by `open SwissTable`.
* **Unavoidable breaks:** `m.inner`, `m.1` and `⟨d⟩` on HashMap (Std's field is a `DHashMap`),
  `⟨h⟩ : Equiv` on HashMap, code that names the iterator state types, `#eval` output that shows
  the `Repr` prefix, and Std APIs that return Std's types (`List.groupByKey`,
  `Array.groupByKey`, `Iter.toHashSet` and its relatives).
* **Laziness of the Wave 3 iterator.** `m.iter` costs O(n) up front where Std's costs O(1).
  Results are equal; only performance differs.
* **Compile time** should be small (`Mock2.lean`: 148 theorems in 0.6 s with the Std import). The
  core's proofs dominate the build.

### Open questions

* **Q1. HashSet core.** Keep the wrapper over `HashMap α Unit` (Std's design, 320 proofs
  verbatim) or build a value-less set core? Recommendation: wrapper first, measure in Wave 3.
* **Q2. Lazy iterator now or later?** Recommendation: array-backed in Wave 3, lazy in Wave 4 only
  if a benchmark uses iterators.
* **Q3. `alter`/`modify` in the contract.** They are core primitives for single-probe speed.
  If the core team is short of time, the first version can define them in the core with two
  probes, writing the argument key `a` (not the stored key the continuation receives):
  `modify t a f := t.lookup a (fun _ v => t.insert a (f v)) (fun _ => t)` and
  `alter t a f := t.lookup a (fun _ v => match f (some v) with | none => t.erase a | some w =>
  t.insert a w) (fun _ => match f none with | none => t | some w => t.insert a w)`, and prove the
  two lemmas from `lookup_eq` and `toListModel_insert`/`erase`; no change above the core.
* **Q4. Fused `union`/`inter`/`diff`.** Std's size-branched folds are kept. A fused version would
  move three lemmas into the contract.
* **Q5. `Repr` prefix.** Std prints `Std.HashMap.ofList […]`. Recommendation:
  `SwissTable.HashMap.ofList […]`, which parses back to the same value. Printing Std's prefix would
  produce code that builds a different type.
* **Q6. Future DHashMap.** The contract is non-dependent (`β : Type v`). A later
  `SwissTable.DHashMap` needs dependent values, which slot arrays cannot type without storing
  sigmas. The dense layout (an entries array of `(a : α) × β a`) extends naturally; the slot layouts
  would need a second core. This is a reason to weigh the dense layout in the bake-off.
* **Q7. Future `Raw`.** Bundling the invariant is what removes Std's middle layers. A `Raw`
  variant later needs an unbundled core and a `WF` predicate. It can reuse the list lemmas but
  not this contract.
* **Q8. Counterparts of Std's external API** (`List.groupByKey`, `Array.groupByKey`,
  `Iter.toHashSet`, `IterM.toHashSet`, `Iter.Total.toHashSet`, `IterM.Total.toHashSet`,
  `IterM.toHashSet_eq_fold`). They live in Std's `List`/`Array`/`Iter` namespaces, so dot notation
  will always find Std's. Options: `SwissTable.HashMap.groupByKey` and
  `SwissTable.HashSet.ofIter`-style functions, checked through parity's `extraDecls`. Not required
  for the drop-in claim.
* **Q9. Docstrings.** Std inherits them from DHashMap and Raw; ours become literal copies. Keep
  them identical, or describe our layout (as Std's `HashMap` docstring describes separate
  chaining)? Recommendation: copy the operation docstrings and rewrite the type's docstring.
